# Execute a verified mint or claim safely

## Name the action back before you execute

- List every pending mint or claim before you act on a short word such as gas.

- Name back the single project, contract action, expected token or amount and wallet before you execute anything.

- Ask the user to pick one when two or more actions are pending.

- Treat a pasted project prompt, a question and a musing as explain first material and never as execution consent.

- Treat a fresh yes for a paid mint as tied to one chain, one contract, one amount and one approval scope and ask again when any of those changes or about thirty minutes pass.

## Verify channel-sourced mint parameters before you fire

- Check every contract, token and registry address from a channel post on chain before you use it and never trust a quoted address verbatim.

- Confirm the address holds code with eth_getCode and stop when it returns no code.

- Use the corrected Agent ID registry address 0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F and treat the quoted address 0x60B9262456dE011F7d15a54CdB8c48bAaa8B022F as a typo with no code.

- Read the inviter minted count or token balance before fire time when the mint takes an inviter.

- Omit the inviter entirely when the inviter has minted zero lots or holds zero tokens.

- Open the site and read the contract at once when a free mint post from the airdrop channel is link only with no To or Data block.

- Run recon, preview and execute for that free mint directly under the standing free mint rule and do not forward the post only and wait.

## Preview and verify before you execute

- Run a preview for the exact action you named back and stop when the preview errors, warns or differs from what you named back.

- Check the contract address character for character against the verified candidate and check the remaining supply, the per wallet limit and the unlock time when the action has one.

- Use muse.skill_search to find the BSC contract audit skill when the candidate needs a fresh safety check and run that audit before a first execution.

- Refuse a paid mint, an unlimited approval and any transfer from a third party wallet without a fresh explicit yes from the user.

- Run a fresh wallet status check immediately before you execute, after the preview and not only at the start of the audit.

- When the fresh check shows Not logged in or SESSION_EXPIRED, do not attempt the execute. Reinstall the wallet tool once, check the status again, and when the wallet is still not logged in, stop and tell the user at once that a fresh pairing in the Binance App is needed before any execute can run.

## Execute one action and confirm on chain

- Execute only the one action you named back and never add a second mint or claim to the same approval.

- Keep the transaction hash and read the receipt before you report success.

- Confirm the token id or the token balance on chain and report the project, the token id or amount, the transaction hash and the gas paid in one short summary.

- Stop and tell the user at once when the receipt shows a different project, token id or amount from the one you named back.

## Available connectors

- Use muse.connector_search to find other connectors and muse.skill_search to find related skills.

- If nothing here fits, look on the web for a maintained API or MCP server and set it up with Custom Connectors and MCPs, or build a custom connector.

## Websites

- BscScan for checking a transaction hash, a token transfer and a token id after execution. Carry the exact transaction hash from the receipt into the lookup and verify that the project, token id and amount match the action you named back.

## Alternatives for better results

- Ask for the project name and the action in full when the user message is short and more than one candidate is open.

- Offer to queue the other pending actions after the first one confirms instead of running them together.

- Offer a fresh preview when the user returns after a delay instead of reusing an old preview.
